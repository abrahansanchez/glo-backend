## Verification policy required before disclosure or cancellation

Four roles must remain separate: caller channel (original signed From), recipient (currently display clientName), booking contact (clientPhone) and verified appointment manager. A shared phone/contact, caller ID, spoken name/date, caller-number agreement or knowing an appointment ID is never sufficient manager authority. The two live milestone bookings demonstrate why a phone cannot be a unique customer/appointment key.

Concrete fail-closed policy for the next slice: allow details/cancellation only after an existing authenticated business owner explicitly authorizes that specific appointment/action through the established staff workflow, OR a separately approved verified customer principal has a persisted appointment-specific management relationship. A plain voice assertion cannot create that relationship. Until a customer-verification/relationship capability exists, phone-only autonomous disclosure/cancellation stays disabled; current milestone appointments do not acquire authority retroactively.

The repository currently provides business-owner authentication, not a verified end-customer login/appointment-manager relationship. This is an explicit implementation dependency, not something to infer from Client.hasConsent or an OTP. If the product chooses managed SMS/OTP, that new capability needs separate approval, consent, rate/abuse limits, challenge expiry/replay controls and an audited relationship policy. OTP proves possession of that channel; for a shared contact it does not identify the individual recipient or grant management of every matching appointment. Use an established approved verification provider/account workflow rather than a homemade authentication scheme. No provider/OTP API, message, secret, sender or authentication mechanism was built/enabled in this round.

Different-number calls must use the same approved independent verification/staff route, not silently replace a saved phone. A caller booking for someone else requires a specifically verified/approved management relationship; agreement to use a contact for booking is not delegation evidence. Existing appointments without such evidence require staff handling, including the two milestone appointments. No automatic name/date/phone fallback should bypass this rule.

## Smallest next implementation scope after authority approval

1. Introduce an injectable verification/authority interface with fake approved grants in offline tests. It returns a server-owned principal/grant with business, allowed appointment IDs/actions, expiry and provenance. No permissive public endpoint that manufactures these from an LLM/call ID. Business staff approval must use existing protected owner authentication and durable audit; customer integration remains blocked until its chosen approved verification capability exists. Expose no appointment count/name/date before authorization; use the same generic verification response for matches and no matches to avoid enumeration.
2. New-call lookup reads Gl? Appointment records fresh, from binding.businessId plus verified allowed-record scope. Old conversation/Retell memory is never a data source. Query canonical E.164 contact only as a locator after authorization, never as permission. Avoid broad digit/name regexes or guessed legacy country aliases. Multiple people/appointments sharing a contact remain distinct records; return only the minimal authorized choices needed to disambiguate. If the grant covers only one record, do not reveal other same-phone matches.
3. Map authorized choices to short-lived server-owned call/business/principal-bound selection references. These are scoped lookup references, not a new customer authentication mechanism. Later calls get new references after fresh verification. Never let a model-supplied business or raw appointment ID choose tenant/authority.
4. prepare_cancellation(selectionRef) loads the selected current appointment. Persist a separate expiring cancellation proposal containing exact appointment ID, business, verified manager grant, original status, updatedAt/revision, canonical service/time/contact hash and expected action. Return only the authorized summary. No mutation on lookup/preparation. The caller must explicitly confirm that exact current cancellation; a changed appointment requires new preparation/confirmation. Both grant and call must still be current, screened and unexpired.
5. commit_cancellation(proposalId, explicit confirmation) claims one durable cancellation command/key/hash, distinct from original bookingCommand. In one transaction consume/fence the action grant/current call ownership, re-read/check the exact expected appointment snapshot on every transaction retry, update only {status:canceled,cancelledAt:applicationClock,cancelledBy:verified Retell action}, and persist command settlement. Extend updateAppointmentAtomically with an explicit expected-state predicate/inside-transaction authorization seam; do not pass a raw model update or rely on a pretransaction check. Match barberId always. Schedule fences serialize release of the old occupied interval. Preserve the appointment/audit; do not delete it.
6. Repeated/concurrent same command returns the persisted cancellation result; same key/different facts conflicts. Already canceled by a separate action is a truthful domain state, not a new success effect. On timeout/unknown commit, reconcile the same durable cancellation command and appointment state read-only. Absence of a command is UNKNOWN, not permission to retry with another key. Do not infer successful cancellation from call end, transcript, analysis, SMS ack or HTTP200 alone.

Future additive storage/indexes (not created here): typed cancellation proposals/commands with durable per-business unique idempotency key and expected snapshot hash; verified management grants supplied by the approved authority capability; a nonunique Appointment {barberId,clientPhone,startAt} lookup index if actual query plans require it. Never add unique clientPhone/name constraints. Grant/selection expiry must be checked directly, not by eventual TTL deletion. Durable uncertain command identity must not be TTL-recycled. Define retention for manager evidence/private hashes separately; do not copy raw OTPs/credentials/whole provider envelopes into call artifacts.

## Scheduling, reminders and future rescheduling

Canceled appointments cease occupying capacity under OCCUPYING_STATUSES confirmed/pending; updateAppointmentAtomically fences the old interval even when the new status is not occupying. Retell notificationsSuppressed=true must remain true across management changes. Do not set reminderSent=true as a fake suppression or flip notifications back on. Existing reminder selection excludes canceled/suppressed records, but a reminder fetched before a concurrent cancellation needs a fresh pre-send status/notification check or reviewed durable delivery outbox in a future notification slice. If notifications are later approved, give them independent durable idempotency and do not equate submission with delivery.

A future reschedule should atomically update the same appointment ID, not cancel then create. Prepare an exact old/new snapshot and fresh availability, lock both old/new date fences in the same existing transaction and retain the original until the atomic move settles. Recheck current authorized grant and exact old version on retries. Persist a separate durable reschedule command and reconcile UNKNOWN without creating a replacement. Keep status occupying (confirmed) at the new interval; current code treats rescheduled as nonoccupying, so do not use that label alone to represent a live moved booking. No date/slot substitution and no silent partial-bundle persistence. Business policy/catalogue/duration changes require fresh preparation rather than reusing old evidence.

## Required future tests before enabling anything

New call with no prior conversation; tenant/agent isolation; no pre-verification enumeration; caller/recipient/contact differences; same phone with multiple recipients and multiple appointments; different incoming number; expired/wrong-action/wrong-record manager grants; staff-only approval path; no raw-ID shortcut; explicit negative/uncertain/mixed replies; stale or concurrently rescheduled appointment; double cancellation/races; transaction retry/unknown commit and read-only reconciliation; old/new fence conflicts; reminder race/suppression; reschedule leaves exactly one original record at old OR new state under failure; no booking/SMS side effects in disabled tests. Enabling cancellation, OTP or notifications requires a separate approved task and connected checkpoint, not a prompt change to the current booking agent.
