## Customer flow (no barber login or mobile app)

1. Retell asks explicit permission to send TWO private verification messages: a link and a separate code. This permission is for phone-possession verification only, separate from contact reuse, appointment-level management delegation, appointment notifications, reminders and marketing.
2. The signed `start_management_verification` tool uses current server call/business/agent/version/epoch/screen/deadline, approved contact and `verificationConsent:AGREED`. The server checks MANAGEMENT canary revision and sender-wide STOP/legacy opt-outs before link submission and again before the Verify code request. If unavailable/uncertain, return a generic rejection and offer owner assistance; do not retry or claim delivery. `VERIFICATION_PENDING` means requests accepted, not carrier/device delivery.
3. The separate Messages adapter sends an application-owned bilingual private URL `https://<backend>/customer/verification/#<random-32-byte-token>`. Only an HMAC of the token is saved. The approved Verify service sends the separate code. No custom Verify-template link support is assumed.
4. Backend serves a bilingual mobile-friendly page at GET `/customer/verification/` (and self-hosted app.js/style.css). No account or app is needed. The fragment never enters the HTTP URL; page immediately removes it from browser history. No analytics/third-party assets. No-store, no-referrer, CSP, frame denial and secure cookie protections apply. Reverse proxy/error monitoring must not log request bodies, cookies, response bodies or SMS bodies; verify that operational prerequisite before activation. A recipient can still deliberately speak a code; the backend cannot erase external conversation-provider recordings.
5. POST `/customer/verification/session`, exact `{token}`, Origin must equal configured backend HTTPS origin; 2KiB body. Atomic one-use token exchange returns `{status:CODE_REQUIRED,csrf,expiresAt}` privately and Secure/HttpOnly/SameSite=Strict `glo_verify` cookie. Token, CSRF and cookie are secret; never pass them to Retell. POST `/customer/verification/complete`, exact `{csrf,code}`, same Origin plus cookie, returns only VERIFIED or generic PRIVATE_VERIFICATION_REQUIRED. Wrong code remains retryable within the five-check limit; consumed/expired link needs a new request, not replay. No appointment existence/details are disclosed.
6. Caller returns to the SAME live call, says completion without the code. Signed `management_verification_status` now takes `{}` and derives latest challenge from authenticated binding; no secret challenge/link reference in tools. VERIFIED returns a non-bearer `authorityRef`, usable only with that signed current call. Lookup still requires explicit appointment/contact grants. Same phone possession alone grants NO appointments. Older appointments require owner-issued grants.

A challenge expires at min(5 minutes, live-call deadline, canary expiry). A replacement request retires prior pending/verified challenge. Durable limits: five sends/contact/hour, two/call/hour, 60-second contact cooldown, five code checks; private endpoints have shared durable 100/minute global and 20/minute hashed-IP counters. Counters use explicit expiry predicates, not TTL timing. Challenge binds tenant/contact hash/call/parent/epoch/admission revision/provider verification ID. Concurrent exchange/check is atomically claimed; terminal success consumes private session. Ended/superseded/unscreened calls, expired admission or revision changes deny completion. Receipt callbacks can settle link delivery but never grant authority. An accepted link send is not delivered; missing receipts stay unmeasured. No new marketing or appointment consent is created.

## Business canary and revocation

`BookingPhaseAdmission` is server-owned configuration in existing tenant identity: `_id` existing business ObjectId string, `enabled:false`, integer `revision`, capabilities subset BOOKING/MANAGEMENT/CALENDAR/NOTIFICATIONS, mandatory `expiresAt`, audit `changedBy`. There is deliberately no customer/Retell admission-write endpoint. Operators must separately authorize a scoped change; a global feature flag alone admits nobody. No admission records were inserted outside isolated tests.

BOOKING gates new staff/workspace APIs and staff tool context/selection. MANAGEMENT gates new delegation, owner grants, verification, scoped lookup and mutations. CALENDAR gates connections/import/export, selected external availability and provider operations. NOTIFICATIONS gates explicit policy/consent and outbound workers. Existing read-only/basic Retell booking and historical suppression are preserved; this is not a retroactive shutdown of existing booking. Required connected calendars fail closed on revocation; they never become free automatically. Normal legacy routes remain as before, including shared scheduling protection for already-managed records.

Admission is read server-side on operations without a positive process cache. Calls snapshot revision at registration; prepared work/consents/sources/connections snapshot it. No widening of an already-admitted call by changing flags. Revocation/expiry/revision change denies pending private checks and new work; native transaction fences serialize against concurrent admission changes. Scheduling final clocks include canary/evidence expiry. Pending notification work is skipped; calendar work cannot dispatch and uncertain remote results remain UNKNOWN for explicit reconciliation. Retaining old rows does not authorize them when a new revision is later admitted. Reconnect/reselect/re-consent in the new scope as appropriate; do not rewrite snapshots to revive pending work. Signed receipts/STOP and local calendar disconnect remain available for settlement/cleanup; revoke does not undo an already-consumed external request. Quiesce workers and review in-flight records before rollback. Never reset budgets, delete grants/appointments or resend UNKNOWN work blindly.

## Calendar volume, rate and freshness

Worker wakes every 5 seconds to inspect durable due sources, without overlapping a local tick. After a successful sync each source is next due 20 seconds after completion, so a healthy one-page source performs at most 3 sync requests/minute, 180/hour, 4320/day (previous 15-second polling: 4/minute). N selected one-page calendars on a connection: 3N/minute, plus OAuth token refresh (normally about once/hour), calendar-list pages on explicit user listing/selection, watch renewal and export reconciliation. The token refresh lease prevents concurrent refresh ownership. A due source lock coalesces concurrent workers; scheduled pre-due work does not call HTTP or advance lastSyncedAt. Explicit user sync intentionally forces a real check and counts against the same connection limit.

Initial setup adds one one-use OAuth exchange, L calendar-list pages per explicit list/selection, the initial sum of selected-source pages, and up to one watch request per source. The steady-state formula does not hide those startup requests.

Each sync page is one HTTP request: up to 20 pages x250 events. Healthy P pages/source gives <=3NP requests/minute; e.g. N=4, P=2 =>24/minute before auxiliary operations. A 410 cursor reset may cost prior incremental pages plus another 20 full pages (bounded up to40), not one request. Busy-only source uses one freeBusy request. Each export consumes an event GET and zero/one write (insert conflict can require one further GET). Reconciliation consumes at least a GET and may perform a guarded write. Watch renewal is normally <=1/day/source, plus stop of old channels; pushes only mark dirty and NEVER refresh the evidence clock.

Durable connection accounting permits at most60 requests per fixed UTC minute bucket (not a rolling-window or Google quota guarantee) across calendar list, token refresh, import pages/freeBusy, watch/stop and export/reconciliation. Attempts are reserved before HTTP and remain counted on uncertain failures. OAuth exchange is separately bounded by one-use ten-minute OAuth state; local disconnect may attempt one remote revocation only while admitted. These are application limits, not proof of Google project/user quota acceptance. Scheduling capacity depends on selected sources/page counts and worker throughput; exceeding the budget yields unavailable required sources, not weaker safety. Failed scheduled sync backs off 30/60/120/240/300 seconds, honors bounded numeric Retry-After up to1hour, and marks unavailable/dirty immediately. No in-method retry except documented410 reset; manual force-sync remains rate-limited. Required source remains unusable if unavailable/dirty/out of range/older than30seconds. Slow batches and high source counts can still cause fail-closed intervals; measure and approve capacity before production.
