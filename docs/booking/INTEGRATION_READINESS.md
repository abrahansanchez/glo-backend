Completion does not accept business/call/appointment identity or return appointments. The caller currently has no automatic path from the spoken interaction/provider code to the required private reference. This blocks real phone-management acceptance, even though fake integration clients can pass the reference directly.

Page must display the server expiresAt (capped by the LIVE call deadline, not always five minutes), avoid third-party scripts, and handle ended/expired calls generically. No automatic confirmation, booking consent or lookup disclosure follows a UI success alone.

## Shared scheduling, durable effects and remaining limits

All scheduling writers inspected converge on atomicScheduleMutation: owner create/update/delete in controllers/appointmentController; legacy AI/SMS/util booking wrappers; idempotent Retell creation; StaffService; AppointmentWorkspace actions; ManagementService. Legacy reminders save delivery metadata only and exclude outbox-managed appointments. New managed edits require an application-owned authorization callback. Legacy AI/SMS writers do not receive one and therefore cannot bypass new delegation/management. Owner deletion of managed records is soft cancellation; unmanaged legacy behavior remains. Staff permissions/prices/durations/hours/time-off and business hours/buffers/conflicts use the actual selected calendar; unassigned old records conservatively block staff, without a backfill.

`services/booking/atomicScheduleMutation.js:194` and `services/booking/atomicScheduleMutation.js:254` register final required-source checks after asynchronous authorization work. `services/calendar/CalendarBoundary.js:4` requires complete buffered range, READY/non-dirty generation, <=30second freshness, current connection and staff membership. Transaction write fences protect local source/configuration/permission changes; synchronous final clock checks enforce freshness and proposal/proof/call deadlines immediately before commit. No provider HTTP runs in the Mongo transaction. Google can change after the last observed cache; no cross-system atomicity guarantee exists.

`services/booking/atomicScheduleMutation.js:199` records deterministic revision/action work in the mutation transaction; `services/booking/atomicScheduleMutation.js:201` runs after consent persistence in that same transaction. Transaction abort rolls back appointment, grant/consent and work. Suppressed historical appointments do not gain consent or notification work. Legacy immediate/reminder paths exclude new outbox records. No automatic back-send, blanket opt-in or appointment reversal after delivery failure.

Calendar worker uses leases, deterministic event identity, current destination/permission/revision, ETags, copy-import deduplication and divergence detection. UNKNOWN uses read-first reconciliation, never blind write retry. Stale jobs cannot publish old facts; disconnect/detach revokes token/source usage and required source uncertainty stays blocking. Revocation after an already-dispatched provider request cannot undo consumption; uncertain post-response state is not declared synced. External edits never authorize local appointment changes.

Notification worker checks current revision/status, explicit consent, suppression, sender-wide opt-out and legacy opt-out state immediately before submission. Known429 retries are bounded; uncertain sends never automatically resend. Signed callbacks are correlated and monotonic; conflicting terminal evidence remains unknown. Booking and delivery/export status are separate. A cancellation or opt-out after dispatch cannot recall a message already submitted; staleAfterSubmission and delivery state expose this residual race. START never silently recreates appointment consent. The source has no authenticated STOP-clear/re-consent endpoint; documented owner-assisted recovery must not be mistaken for a currently implemented automated API.

Additional operational limits: GLO booking/calendar/notification API flags are GLOBAL authenticated feature switches, not per-business canary allowlists. Retell sandbox call admission is explicitly business/agent/version scoped. Before enabling global GLO APIs on the existing service, separately approve that exposure or implement a reviewed business canary gate; hiding UI does not scope an endpoint. No canary setting is invented here. Worker stop clears future ticks; an already-running bounded sync batch can drain and cannot be described as instantly canceled. Rollback must quiesce active work. Export currently manages active occupying copies: canceled/completed/no_show non-occupying transitions enqueue REMOVE while local appointment history remains; do not promise external historical-event retention without approving that policy.
