## Ownership decision and account entry

Confirmed product decision: preserve existing ownership. A Barber account is its own business owner; discovery combines that ONE business and current memberships in other shops. There is no multi-business ownership relationship or tenant migration. An independent owner can join several shops without losing their own customers, subscription, service catalogue, calendars or routing. A staff-only new account has no owner onboarding obligation.

Existing POST /api/auth/register accepts the existing {name,email,phone,password} and optional entryMode:"staff". It creates an ordinary existing account with staffOnlyAccount=true; it does NOT verify email/phone, grant membership, create billing, provision a number or send messages. Existing register returns201/message, then POST /api/auth/login returns the existing Bearer JWT plus barber.staffOnlyAccount and workspaceDiscoveryPath. Existing email duplicate-account behavior remains; accept never creates an account. Phone must be canonical E.164 for invitations; typed account email/phone alone are never verification proof. Logging in does not run subscription or phone onboarding. Mac must use workspace discovery for staff entry, rather than redirecting every login into owner billing.

## Common API rules

All routes below are under `/api/booking/v1`, require existing Bearer JWT, and use success `{data:...}`, errors `{reasonCode}`. Owner/tenant/calendar authorization is server-owned. Body bound16KiB; invalid parser request400/413; FORBIDDEN403; domain conflicts409. Disabled invite API404 INVITATIONS_DISABLED; opted-in but missing invitation prerequisites503 INVITATION_CONFIGURATION_REQUIRED. APIs do not accept a client role or tenant assertion as authority. Invitations need BOOKING canary for the shop and matching admission revision. Owner setup/list actions are possible before payment; calendar/booking access requires the BUSINESS owner's actual entitlement. Staff never buys an owner subscription.

## Private invitation and mobile return

Existing SMS implementation delivers a bilingual HTTPS link `/staff/invitation/#<random32byte-token>`; provider accepts is not delivery. Link page is served by backend, no login or automatic acceptance, no third-party assets/analytics. It immediately clears fragment history and offers one explicit button to approved STAFF_INVITATION_MOBILE_RETURN_URL with token in fragment. No token in query/referrer/logs/list APIs; only HMAC digest stored. Intended contact is encrypted using existing AES-GCM vault with invitation-specific AAD. Backend page is usable as a handoff; Mac must implement that configured HTTPS universal/web link destination, sign-in/signup, token-in-memory continuation, preview, consent to private OTP, code input and explicit Accept. Do not put tokens/codes in analytics, crash reports, clipboard logs or Retell. No customer appointment-management proof is reused as staff authority.

Phone possession must be proven through the existing Verify adapter for THIS signed-in account and THIS invitation. An unverified account profile phone or typed email is not proof and is not used as authority. The provider verifies the encrypted intended invitation contact; the proof is bound to the account that explicitly started it. Another account cannot reuse that proof even with the token/code. Existing accounts may retain their different business/profile phone unchanged. Invalid tokens/proofs return generic INVITATION_UNAVAILABLE, not account existence. Invitation expires min(24h, canary expiry); OTP min(5min, invitation expiry); five checks, one code dispatch/no automatic resend; owner10invitation requests/hour and recipient5proof starts/hour, durable counters. Counters/expiry are read directly, not TTL deletion. Explicit replacement is the recovery after unknown/failed verification, not an unsafe retry. Admission revision change/expiry, owner revoke, calendar revision/active-state change, membership update or leaving prevents stale acceptance. Membership revocation invalidates cursors, selected workspace access and prepared mutations even if later re-granted. Durable invalidation works across disabled feature restarts; history remains. A manager cannot invite/escalate or administer owner billing/routing.

## Shop commercial and phone lifecycle

Shop setup reuses existing account/business, services/hours validators, progress, authoritative readiness, Subscription, PhoneNumberAssignment, new-number/forward-existing provisioning, ownership/idempotency and recovery. Existing independent business with services, billing or phone data cannot silently convert: EXISTING_BUSINESS_CONVERSION_REQUIRES_OWNER_ASSISTANCE. Staff-only account may explicitly start its OWN blank shop; memberships remain independent.

New shop requires configured GLO_SHOP_STRIPE_PRICE_ID, never client price. Optional GLO_SHOP_TRIAL_DAYS is explicit configured0..365; absent means no configured trial offer and no trial parameter. No hardcoded individual14day trial applies. Existing POST /api/billing/create-checkout-session with Idempotency-Key16..128 safecharacters invokes configured shop checkout when explicitly enabled. Server creates customer/checkout with stable idempotency keys; response PAYMENT_PENDING is NOT payment readiness. Unknown response retains same command key, no automatic retries. Existing `/api/billing/trial/start` rejects shop/staff; shop trial/subscription must use configured Checkout and authenticated subscription events.

Only existing Stripe-signature-verified customer.subscription.created/updated/deleted events update shop commercial proof. Tenant metadata, existing customer identity, configured price, subscription ID, status, event ordering and trial expiry checked. Checkout completion/redirect and late invoice callbacks cannot activate a shop. Duplicate events repair mirrors without duplicate subscriptions; older events cannot reactivate canceled/past-due subscription. Signed settlement continues with retained price identity even while feature disabled. Provider receipt/Stripe commercial configuration remains UNVERIFIED live.

Then existing POST `/api/phone/setup/start` {productType:shop}, GET `/api/phone/setup/readiness`, POST `/api/phone/number-strategy` {strategy:new_number|forward_existing,...existing forwarding fields}, existing status/test/recovery routes. Actual owner, canary and verified current subscription required before provider operations. Shop identity is preserved, never forced individual. No porting expansion. Existing routing/mobile/human takeover and number ownership unchanged. Staff calendars/permissions never grant call handling rights. New-number/forward-existing share proven durable assignment and mirror-recovery mechanisms; controlled provider acceptance still pending.
